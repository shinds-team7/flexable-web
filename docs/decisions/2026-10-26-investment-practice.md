## 범위와 완료 조건

기존 `/invest`와 `Invest.tsx`, `simulation` 패키지의 계산·응답을 유지한다. 공통 메뉴의 `/invest` 표시만 **투자 인사이트**로 바꾼다. 신규 `/simulation`에 **투자 시뮬레이션**을 만들고 별도 `practice` 패키지와 `/practice/*` API로 연결한다. 시장 자료 읽기와 수집 기능 확장은 허용하되 기존 API의 필드·응답은 바꾸지 않는다.

완료 조건은 업종 선택 → 투자금 입력 → 무작위 종목 선정 → 사건 사이 구간을 3초에 재생 → 공시 모달에서 방향·매매 선택 → 재생 재개 → 결과 확인이다. 서버 계산, 실제 OHLC 캔들, 미래 자료 비노출, 거래 중복 방지, 데이터 부족 안내, 기존 정책 테스트와 계약 테스트 통과까지 포함한다. 예시 환경 검증과 운영 데이터 검증은 따로 보고한다.

## 현재 구현과 부족한 자료

현재 `DailyBar`·`DailyPrice`는 수정 종가와 거래량만 보관한다. `Instrument`에는 업종이 없고, `POST /simulations/run`은 정해진 납입만 계산한다. 기존 사건 제목·설명에는 급등/급락과 사후 수익률이 들어 있다. 이 제목을 문제로 사용하지 않는다.

| 필요한 자료 | 보충 방법 | 확인 상태 |
|---|---|---|
| 시가·고가·저가·종가 | 기존 키움 `ka10081` 응답의 `open_pric`, `high_pric`, `low_pric`, `cur_prc`를 함께 저장 | 공식 가이드의 필드 확인. 인증된 실제 응답 검증은 미수행 |
| 회사 업종명 | 기존 키움 종목정보 리스트 `ka10099`의 `upName` | 공식 가이드에서 업종명 필드 확인. 실제 응답 검증 미수행. 누락 가능한 필드라 빈 값은 제외 |
| 사건 | 기존 `event_sources`의 DART 접수번호·접수일·원문 제목·URL | 과거 급변동 사건에 연결된 일부 공시라는 표본 편향을 안내 |

출처(2026-10-26 확인): [키움 일봉 가이드](https://openapi.kiwoom.com/m/guide/apiguide/07/ka10081), [키움 종목정보 리스트](https://openapi.kiwoom.com/m/guide/apiguide/01/ka10099). 대안으로 [OpenDART 기업개황](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019002)의 `induty_code`도 확인했지만, 별도 코드표가 필요하므로 첫 구현은 키움 업종명을 사용한다.

키움 응답의 네 가격은 같은 수정주가 기준이어야 한다. 공급자가 주는 부호를 기존 가격 파서와 같이 정규화하고, 양수 및 `low <= open, close <= high`를 검증한다. 종가로 시가·고가·저가를 합성하지 않는다. 원래 종가 경로는 유지하고, OHLC 누락·잘못된 봉은 신규 기능에서 제외한다.

## 수집과 준비 상태

1. `ingest`에서 OHLC를 저장하도록 확장하고 새 Flyway 마이그레이션으로 nullable 필드를 추가한다. 기존 종가 조회 결과는 동일하게 유지한다.
2. 기존 기간의 OHLC를 다시 받는 보충 수집을 추가한다. 최근 10일 재조회만으로 과거 OHLC가 채워졌다고 간주하지 않는다. 종목별 진행 상태를 두고 다음 실행에서 이어 받는다.
3. worker에서 KRX 종목 선정은 유지하되, 키움 `ka10099` 목록의 종목코드로 업종명을 보충한다. KRX가 성공해도 업종 보충을 실행해야 한다. 기존 키움 목록 캐시를 재사용하고 업종 원본명·확인일·출처를 별도 저장한다. 실패하면 직전 성공 분류를 유지한다.
4. 업종명은 NFC 정규화·앞뒤 공백 제거 후 같은 이름끼리 묶는다. 내부 categoryCode는 그 UTF-8 이름의 SHA-256 앞 24자리(소문자 hex), 분류 규칙 버전은 `KIWOOM_UPNAME_V1`이다. 이는 공식 업종 코드가 아닌 내부 식별자임을 명시한다. 코드 충돌은 오류 처리하며 다른 이름을 합치지 않는다. 빈 값·누락은 분류 불명으로 제외한다. 현재 업종을 과거 기간에 적용함을 안내한다. 반도체·AI 같은 별도 테마는 이 스펙의 자동 분류 대상이 아니다.
5. 업종, 연속된 유효 OHLC 120거래일, 그 구간에서 출제 가능한 공시 1건 이상이 모두 있는 현재 수집 대상 STOCK만 후보로 쓴다. ETF·분류 불명·공시 없음·중간 OHLC 누락은 제외한다. 공시의 접수일 뒤에도 5거래일이 있어야 한다.
6. 종목별 최근 유효 120거래일 구간 하나를 고정한다. 동일 업종의 후보 종목은 균등 무작위로 고른다. 후보 0개면 시작을 거절하고 데이터 준비 안내를 표시한다. 다른 업종이나 예시 자료로 몰래 대체하지 않는다.

개발용 fake 자료는 OHLC·업종·공시를 일관되게 제공하고 `isSample=true`를 응답·화면 전체에 표시한다. 실제 자료와 예시 자료를 한 실행에 섞지 않는다. 수집 실패 시 기존 성공 자료는 보존한다. 브라우저 요청 중 외부 시세 API를 호출하지 않는다.

## 화면과 진행

- 시작 화면: 업종, 투자금(1만~1억원), 초기 배분(50% 예산으로 매수·나머지 현금), 과거 계산 고지, 예시 표시를 보여준다. 종목당 가격이 높아 최초 매수 수량이 0이면 현금으로 시작함을 알린다.
- 진행 화면: 종목·업종·현재 날짜, 빨강 양봉/파랑 음봉/중립 보합 캔들, 현금·보유 수량·주식 평가액·총자산·손익·수익률, 일시정지와 종료. 수치는 모두 서버 응답을 표시한다.
- 캔들은 하루 OHLC 전체를 한 번에 추가한다. 장중 체결 경로는 없으므로 틱 흐름을 꾸며내지 않는다. 진행 요청 한 번은 다음 사건이 나오는 거래일 또는 마지막 봉까지 진행하고, 새로 공개된 봉마다 서버가 계산한 자산(`frames`)을 함께 준다. 화면은 이 구간을 거래일 수와 관계없이 3초에 나눠 그린다(하루 간격 = 3초 ÷ 구간 거래일 수). 구간이 길면 봉이 빨리, 짧으면 천천히 지나간다. 구간 안에서 확정된 판정·다음 사건은 재생이 끝난 뒤 보여 준다. 숨긴 탭에서는 자동 진행을 멈춘다. 다음 요청은 앞선 요청 완료 후 보낸다.
- 사건 모달: 원문 공시 제목·접수일·원문 링크, 긍정/부정 예상, 매도/유지/매수, 매매 비율 25/50/100%. 둘 다 선택한 뒤 확인하면 닫고 재생한다. 유지에는 비율 0을 쓴다. 포커스 가두기·복귀·키보드 조작을 지원하고 닫기/ESC만으로 진행되지 않는다.
- 선택 후 다음 거래일 시가에 가상 체결한다. 잔액 부족으로 1주도 살 수 없으면 미체결로 표시하고 진행한다. 종료·화면 이탈·재시작 시 타이머와 진행 요청을 정리한다.
- 결과: 총자산·손익과 선택별 실제 후속 등락을 보여준다. 매수/매도 선택 자체를 정답/오답으로 채점하거나 수익률 순위를 만들지 않는다.

## 사건과 미래 자료

DART 목록에는 정확한 공시 시각이 없으므로 **접수일 당일 종가 이후** 공개된 것으로 일관되게 취급한다. 휴일 접수면 직전 거래일 봉 뒤, 다음 거래일 시가 전에 보여준다. UI에는 접수일과 재생 기준일을 구분한다. 원문 제목만 쓰고 기존 급등/급락 제목·사후 설명·AI 원인 추정을 노출하지 않는다.

첫 봉 이전 공시와, 첫 사건 전 14거래일(시작 구간)을 채우지 못하는 공시는 제외한다. 한 실행에서 최대 3건을 접수일·접수번호 순으로 고르고, 접수번호를 중복 제거한다. 같은 재생 위치의 공시는 첫 한 건만 사용한다. 직전 문제의 다섯 번째 후속 거래일 판정이 끝난 뒤의 문제만 출제한다. 앞으로 출제될 사건 목록·가격·정답은 시작/진행 응답에 포함하지 않는다. 공개 과거 자료를 외부에서 찾아보는 것까지 막는 시험 서비스는 아니다.

## 서버 상태와 개인정보

#88에서 `Privacy.tsx`(제3·4조)와 `privacy-web.md`에 아래 처리 내용을 반영했다. 운영 공개 전 개정 고지·시행일은 운영자가 확인한다.

- 로그인 없이 체험한다. 서버는 무작위 256비트 이상 세션 토큰과 투자금·선정 종목·진행 위치·거래·응답 재전송 정보를 메모리에만 두고 계정과 연결하지 않는다.
- 시작 후 30분 절대 만료, 서버 재시작 시 소멸, 명시적 종료 시 삭제. 종료하지 않고 이탈한 세션도 만료된다. 만료 정리는 최대 1분 간격이다. DB·브라우저 영구 저장·외부 전송 없음. 브라우저는 컴포넌트 메모리만 사용한다.
- 한 인스턴스에 최대 1,000세션. 정리와 자리 예약을 원자적으로 수행하고 초과 시 503을 반환한다. 세션당 최대 120봉·3문제·128명령으로 메모리 사용량을 제한한다. 서비스가 여러 API 인스턴스로 늘면 공유 상태 설계를 먼저 갱신한다.
- 세션 토큰은 URL이 아닌 요청 본문에만 담는다. 요청 본문·토큰·투자금·선택 기록은 접근/오류 로그에 남기지 않는다. 응답에는 `Cache-Control: no-store`를 붙인다. 외부 공시 링크는 `noopener noreferrer`로 연다.
- 각 변경은 세션 잠금 안에서 버전 확인·거래·응답 기록을 원자 처리한다. 같은 `commandId`와 같은 본문 재전송은 원래 응답을 돌려주고 추가 진행/체결하지 않는다. 같은 ID로 다른 본문을 보내거나 오래된 버전이면 409다. 만료된 세션은 재전송도 410이다.
- 시작도 `startId`로 중복을 막는다. 동일 ID·동일 입력은 기존 세션의 시작 응답을 돌려준다. 명시적 종료·만료 시 시작 ID도 제거하며 이후 같은 ID 요청은 새 실행이다. UI의 재시작은 항상 새 ID를 생성한다. 실행 중에는 선정 당시 시장 자료 스냅숏을 고정해 worker 갱신이 진행 결과를 바꾸지 않게 한다.
- 정상 진행이 끝나면 `FINISHED`로 두고 결과는 원래 만료 시점까지 재조회 가능하다. 종료 API는 즉시 삭제하고 같은 토큰 반복 종료도 204다.

## 구현 순서와 검증

오류 계약은 다음과 같다. 기존 오류 응답 형식 `{code, message, fields?}`를 유지한다.

| 상태 코드 | code | 조건 |
|---|---|---|
| 400 | VALIDATION_FAILED | 금액·업종 코드·토큰 형식·매매 비율 등 잘못된 입력 |
| 409 | PRACTICE_CONFLICT | 오래된 version, 동일 명령 ID의 다른 입력, 현재 상태에서 불가능한 진행/선택 |
| 410 | PRACTICE_EXPIRED | 만료·재시작·삭제 등으로 토큰을 찾을 수 없음(end는 204) |
| 503 | PRACTICE_UNAVAILABLE | 해당 업종의 유효 자료·출제 가능한 후보 없음 |
| 503 | PRACTICE_CAPACITY | 활성 세션 상한 도달 |

categories 조회 실패는 503 PRACTICE_UNAVAILABLE이다. 알려진 업종이나 사라진 업종의 후보가 0개면 start는 503, 존재한 적 없는 업종 코드는 400이다. 409를 받은 화면은 `/practice/state`로 현재 상태를 읽고, 410이면 시작 화면에서 만료 안내를 한다. 네트워크 실패는 같은 명령 ID로 재시도하며 자동으로 새로운 매매 명령을 만들지 않는다. 진행 상태(10-27): 1·3·4·5는 완료(#86·#88). 2는 위 "현재 구현"의 묶음 저장 방식으로 대신했고 실제 응답 검증은 남았다. 6은 로컬 검증 명령·CI까지 완료, 운영 연결 검증은 남았다.

1. 이 스펙 PR 검토·병합 → 최신 main rebase·변경 문서 재확인.
2. 수집·저장·보충 수집: 파서 fixture, OHLC 결측, 코드 미매핑, 수정주가 일관성, 부분 실패·재시도 검증.
3. 별도 practice 엔진: 정책 JSON을 읽는 테스트, 현금 보존·매도 초과 금지·소수점/경계값·보합 검증.
4. 세션 API: 무작위 후보·빈 후보·미래 자료 없음·중복 명령·동시 요청·만료·최대 세션·no-store 계약 테스트. `practice -> market` 의존만 추가하고 아키텍처 검사에 반영.
5. 신규 화면과 메뉴 연결: `npm run gen:api`, mock API 개발, 키보드 모달·구간 3초 재생·재시도·이탈·재시작·예시 표시 검증. 기존 `Invest.tsx`와 `simulation` 패키지 diff가 비어 있는지 검사.
6. 공통 검증 명령을 모두 실행하고 결과 보고. 운영 연결·보충 수집은 사람이 서버 환경 변수와 실행을 확인한 뒤 별도 검증한다. 운영 DB와 `.env`를 이 작업에서 직접 변경하지 않는다.

사용자 준비 사항은 운영 연결 검증 단계에서 worker의 기존 `DART_API_KEY`, `KIWOOM_APP_KEY`, `KIWOOM_SECRET_KEY`가 실제 호출 가능한지 확인하는 것이다. 키 값은 채팅이나 저장소에 전달하지 않는다. 새로운 API 가입이나 업종 코드표 제공은 현재 설계의 전제조건이 아니다.
