# F7을 투자 성향에 따른 목표 달성 시나리오로 개편

- 날짜: 2026-10-29 · 결정한 사람: 사용자 · 관련: Issue #115, 성향 결과 의존 #123
- 영향: 기획 / 웹 프론트 / 웹 백엔드 / 신규 AI 서버 / 개인정보 처리 설계
- 상태: **제품 방향 결정. 11-03 MVP 계산 정책·API 확정**([policies §7](../policies.md), `POST /goal/scenarios`, #174), **서버 계산·회원 저장(#194), `/goal` 연결(#202), 회원 OpenAI 조합 연결(#228) 병합. AI 문구 검사 수정(#249) 병합, 실제 AI 응답 운영 확인은 별도**. 아래 "11-03 MVP 확정"이 MVP 범위의 기준이다. 10-29의 `/goal/demo` 고정 예시 시연 화면(아래)은 11-03에 뺐다. 이 기록을 담은 spec-change PR이 병합되기 전에는 기존 운영 기능의 정책·계약이 유지된다.

## 결정

F7을 기존의 저축 속도·기한 산술과 AI 실천 문장 안내에서, **투자 성향·현재 마련한 돈·목표 금액·목표 기한·매달 저축/투자 가능한 금액을 바탕으로 여러 금융 조합을 비교하는 기능**으로 바꾼다.

1. 자산군·상품 유형뿐 아니라 **실제 금융상품·금융회사·종목명과 배분 비중을 포함한 맞춤 시나리오를 허용한다.** 기존의 "맞춤 상품·종목·비중 제안 제외"는 새 F7에 적용하지 않는다. 상품·종목을 제안한다는 사실을 "단순 정보 나열"이라고 설명하지 않는다.
2. 적금·주식·ETF 등 서로 다른 조합과 납입 계획을 비교하고, 목표 달성 가능성·손실 가능성·결과 범위·조건을 함께 보여 준다. 사용할 상품 범위·개수·비중 한도는 후속 정책에서 정한다.
3. 결과는 AI·계산 모형에 따른 추정치이며, 실제 수익·목표 달성·원금 보장을 뜻하지 않는다고 고지한다. 근거 없는 수익률·확률을 생성하거나 달성이 어려운 목표를 가능한 것처럼 꾸미지 않는다.
4. AI 서버는 **아직 없다. 새로 구축할 예정이고 FastAPI가 후보**다. FastAPI 채택·배포 구조·소유 저장소는 확정 전이다. 이번 변경에서 서버를 만들거나 기존 Spring API를 교체하지 않는다.
5. 성향 퀴즈는 팀원이 별도로 진행한다. 이 작업에서는 퀴즈 문항·채점·유형·화면·저장을 수정하지 않는다. F7은 향후 확정될 성향 결과를 입력으로 받는 경계만 다룬다.

실제 매매·자동 주문·계좌 운용·가입 중개·개인 데이터 판매를 이번 기능에 추가하는 결정은 아니다. 기존 과거 사건 설명이나 F9 상품 카드의 범위를 함께 확대하지 않는다.

## 기존 구현과 달라지는 점

| 항목 | 현재 구현(v1) | 새 F7 방향(v2, 구현 전) |
|---|---|---|
| 입력 | 목표·현재 금액·월 저축 속도, 앱 연동 값 | 성향 결과와 목표 조건, 필요 시 손실 감내·유동성 조건 |
| 비교 | 속도 유지 / 기한 맞추기 / 6개월 늘리기 | 실제 상품·종목과 비중·납입 계획이 다른 여러 조합 |
| 계산 | Spring `GoalMath`의 수익 없는 산술 | 신규 계산 서비스의 수익·위험 분포와 시나리오 비교 |
| AI | 계산된 숫자를 자리표시자로 설명, 상품명 차단 | 검증된 상품 목록·계산 결과를 토대로 조합·차이를 설명 |
| 결과 | 필요 월 금액·예상 도달 월·행동 안내 | 목표 달성 추정 확률·손실 가능성·결과 범위·조정 대안 |
| 서버 | Spring에서 OpenAI 직접 호출 | 웹 서버와 신규 AI/계산 서버의 연결 방식 설계 필요 |

현재 `goal-ai.md`의 상품명 차단·금지어 검사는 **v1 코드의 동작 기록**이다. 이를 v2의 제품 금지 규칙으로 재사용하지 않는다. 모델 검증·출처 확인·원금/수익 보장 방지는 v2에 맞게 별도로 설계한다.

## 설계 제안: 숫자 계산과 AI 설명의 역할

아래는 구현을 위한 제안이다. 알고리즘·API 필드·한도를 확정한 계약은 아니다.

웹 화면 → Spring 웹 서버(인증·입력·목표 관리) → 신규 AI 서버(후보 FastAPI: 후보 조합·수치 계산·설명) → Spring 검증 → 웹 결과 비교 흐름을 우선 검토한다. 브라우저가 AI 공급자 키를 가지거나 앱 서버 DB에 직접 접근하는 구조는 사용하지 않는다.

- **계산 엔진**: 납입·만기·세금/비용 가정, 배분, 시나리오별 자산 경로·목표 달성 비율·위험을 계산한다. 같은 입력·자료 버전·모형·난수 seed로 수치 결과를 재현할 수 있게 한다. 계산이 FastAPI 서비스 안에 있어도 ADR-3의 서버 계산 원칙에 해당한다.
- **생성형 AI**: 확인된 상품 목록에서 후보 조합을 제시하고 계산 도구를 호출하거나 계산된 조합을 설명할 수 있다. 어떤 방식을 쓸지는 후속 설계로 정한다. 상품 코드·비중·수익률·확률은 계산 엔진과 목록 검증을 거친 값만 결과로 채택한다. AI가 말한 숫자만으로 확률을 표시하지 않는다.
- **웹 서버**: 회원·목표 관리의 정본을 유지한다. 시나리오 저장·삭제·사용량·재계산 기준·AI 서버 인증과 장애 처리는 새 계약에서 정한다.
- **장애 처리**: 계산 실패와 설명 실패를 구분한다. 설명만 실패하면 검증된 계산 결과와 기본 설명을 보여 주는 방식을 검토한다. 확률 계산이 실패했는데 기존 저축 안내를 새 투자 예측 결과처럼 반환하지 않는다.
- **긴 계산**: 실행 시간·동시 요청을 측정한 뒤 요청 안에서 끝낼지 작업 상태 조회 방식으로 할지 정한다. 무거운 계산을 단순히 FastAPI `BackgroundTasks`로 넘기는 것으로 설계를 끝내지 않는다([공식 문서](https://fastapi.tiangolo.com/tutorial/background-tasks/#caveat)).

## 입력과 상품 자료에서 정할 것

| 구분 | 후속 정책·계약에 필요한 결정 |
|---|---|
| 성향 결과 | 팀원이 정한 결과 코드·버전·조회/전달 방식. 기존 브라우저 선택값을 퀴즈 결과라고 간주하지 않음 |
| 시작 금액 | 앱 확정값 / 홈 직접 수정값 / 목표 직접 입력값의 우선순위와 기준일. 기존 F7은 홈 직접 수정값을 쓰지 않으므로 명시적 변경 필요 |
| 납입 | 월 가용액·첫 납입일·월초/월말·중도 인출·납입 중단·기한 변경 가정 |
| 위험 조건 | 투자 선호와 실제 손실 감내 능력을 구분. 비상금·필수 지출·필요 인출 시점 등 무엇을 입력받을지 결정 |
| 상품 목록 | 실제 상품 코드·이름·종류·거래 통화·금리/만기/자격·최소 가입/매수액·유동성·출처·기준일·자료 버전 |
| 후보 조합 | 비중 합·상하한·집중도·리밸런싱·잔돈·정수/소수 주·혼합 통화 처리. 목표에 맞추려고 자동으로 위험 한도를 높이지 않음 |
| 비용·세금 | 수수료·세금·배당·환율·물가 중 포함 항목과 계산 규칙. 누락한 항목은 가정에 표시 |

성향의 공격성이 높다는 이유만으로 기대수익률을 높여 대입하지 않는다. 액티브 운용·높은 변동성·높은 기대수익은 서로 같은 개념이 아니다. 금리와 가입 조건이 확인된 적금은 납입 계획에 맞춰 계산하고, 미검증 정책 적금 규칙(#113)을 확정 상품 조건처럼 사용하지 않는다.

## 확률·위험 표시에서 정할 것

"달성 확률"의 사건 정의부터 정한다. 예를 들어 **기한 말의 비용 반영 자산이 목표액 이상인 경로의 비율**과 **기한 안에 한 번이라도 목표를 넘은 비율**은 다르다. 어느 것을 쓸지 계약 전에 결정한다.

- 자료 제공처·기간·표본 편향·배당/상장폐지·환율 처리, 수익률 분포·자산 간 상관·리밸런싱을 정의한다. 보유한 일봉 자료만으로 검증된 미래 확률이 이미 만들어졌다고 보지 않는다.
- 역사적 구간 재표본화나 모형 기반 몬테카를로 등 계산법을 비교·검증하고 정한다. 모형·자료 버전, 표본 경로 수·기준일·주요 가정을 결과와 함께 남긴다.
- 비교 후보 지표: 목표 달성 추정 확률, 만기 자산의 하위/중앙/상위 분위값, 총 납입원금보다 적을 확률·미달 금액, 스트레스 상황의 결과. 사용할 분위수와 "위험 낮음/중간/높음" 구간은 임의로 확정하지 않는다.
- 중간 최대 하락을 표시한다면 납입금 때문에 위험이 작아 보이지 않도록 산식을 먼저 정한다. 만기 손실 확률과 중간 하락 위험을 같은 값으로 취급하지 않는다.
- 확률은 **정해진 가정 아래의 모형 추정**이다. 과거 수익률이 미래를 보장하지 않으며, 모의실험에서 성공 경로가 없거나 전부 성공했어도 실제 가능성 0%·100%로 단정하지 않는다. 표본 오차와 모형 불확실성도 구분한다.

고지 초안: "이 결과는 입력한 조건과 과거 자료·계산 모형을 바탕으로 AI와 계산 서버가 만든 추정 시나리오예요. 실제 수익과 목표 달성 여부를 보장하지 않으며, 투자한 원금의 일부 또는 전부를 잃을 수 있어요. 자료 기준일과 계산 가정을 함께 확인해 주세요."

표현·수치 표시 기준은 확정 전이다. 고지 문구만 붙이고 근거 없는 확률·수익률을 게시하는 방식은 사용하지 않는다. 수익률의 산출 가정·비용·과거 실적의 한계를 함께 살펴야 한다는 점은 [SEC 투자자 안내](https://www.investor.gov/introduction-investing/general-resources/news-alerts/alerts-bulletins/investor-bulletins-47)를 참고했다(계산 결과 설명의 참고 자료이며 국내 법적 허용 근거가 아님).

## 목표가 어려울 때의 결과

사용자 예시는 **초기 자산 0원·매달 50만 원·36회 납입이라고 가정하면 총 납입 1,800만 원, 목표 1억 원과의 차이 8,200만 원**이다. 시작 자산이 있으면 결과는 달라진다. 이 차이를 채울 수익률이나 달성 확률을 임의로 만들지 않는다.

여러 조합을 계산해도 현실적인 달성 경로가 부족하면 그 결과를 그대로 보여 준다. 월 납입액 늘리기·기한 늘리기·목표 조정·초기 자금 추가 중 무엇을 바꾼 대안을 비교할지 정한다. 모든 사용자에게 목표를 달성하는 상품 조합을 반드시 찾아 주는 기능으로 약속하지 않는다.

## 공개 운영과 개인정보에서 확인할 것

제품 범위에서 맞춤 상품·종목·비중 제안을 허용한 결정과, 해당 서비스의 법적 제공 요건을 충족했다는 판단은 별개다. "AI 예측치" 표시는 법적 면제나 등록·신고를 대신하는 근거로 취급하지 않는다. 개별화된 제안·과금·대화 방식·가입 연결 등 실제 서비스 방식에 따른 적용 여부를 확인한다. [금융위원회 안내](https://www.fsc.go.kr/no010101/82887)는 개별 투자자문과 불특정 다수에 대한 조언의 범위를 구분한다. 이 기능의 구체적 해당 여부는 아직 판정하지 않았다.

신규 서버의 운영 주체·호스팅 위치·보관 기간·LLM 제공처와 전송 항목을 정해야 한다. 현재 웹 방침은 성향 결과·상품별 배분을 신규 서버에 보내는 처리를 구현한 문서가 아니다. 실제 저장·전송을 추가하는 PR에서 `Privacy.tsx`·`privacy-web.md`, 삭제·로그·백업 규칙을 함께 맞춘다. 이번 문서 변경은 개인정보 저장·전송을 새로 실행하지 않는다.

## 구현 전 후속과 완료 조건

1. 성향 결과의 전달 경계만 팀원과 맞춘다. 퀴즈 구현에는 관여하지 않는다.
2. 시작 자산·상품 범위·배분 제한·확률 정의·자료와 검증 방법·MVP 범위·일정을 확정한다. 기존 11/1 동결 전에 전체 개편을 마칠 수 있다고 가정하지 않는다.
3. 웹 ↔ 신규 서버 책임과 오류/상태·저장 수명·재계산 규칙을 정하고 OpenAPI·계산 정책·fixture를 먼저 추가한다. 기존 `/me/goal`·`/me/goal/coach`를 유지/확장/대체할지도 이때 정한다.
4. 계산 검증: 수익률 0의 납입 합, 금리 확정 적금, 비중 합·금액 보존, 불가능/초과 목표, 손실·급락·자료 부족·비용·통화·재현성. 확률의 예측 성능과 민감도를 따로 평가한다.

## 11-04 AI 문구 검사 조정(사용자, #243)

- 운영에서 AI 조합이 문구 검사에 걸려 예시 조합만 나왔다. 검사가 정책보다 넓게 구현돼 있었다: 아라비아 숫자를 하나라도 쓰면 막아 AI에게 보낸 상품·지수 이름(S&P 500 등)과 기한도 걸렸고, "보장"이라는 글자만 있으면 막아 "수익이 보장되지 않아요" 같은 주의 문구도 걸렸다.
- 이 문서 위쪽의 원칙(근거 없는 수익률·확률을 만들지 않는다, AI가 말한 숫자만으로 확률을 표시하지 않는다, 원금·수익 보장을 막는다)은 그대로다. 그 원칙에 맞게 **숫자는 서버가 확인할 수 있는 것만 허용**한다: AI에게 보낸 이름 속 숫자·기한·목표 금액·금리·세율, 그 시나리오의 비중과 같은 %. 그 밖의 금액·%·배수는 계속 막는다. 보장 표현은 단정만 막고 부정문은 허용한다(policies §7-6).
- 걸린 이유(규칙·시나리오·칸)는 서버 로그에 남기고 문구는 남기지 않는다. 프롬프트는 goal-scenario-v3로 바꿔 쓸 수 있는 숫자와 해설에 담을 내용을 알려 준다. 글자 수 한도(제목 20·요약 40·해설 300자)와 데모 조합 문구는 그대로다.

## 11-05 AI 해설 구체화(사용자, #278)

- 300자 해설로는 왜 이 조합을 받았는지 설명하기 어려워, 위 "글자 수 한도(해설 300자)"를 조정한다. 해설의 글자 수 검사와 계약의 `maxLength`를 없앤다(제목 20자·요약 40자는 그대로). 비용과 응답 시간은 응답 토큰 상한으로 막으므로 상한을 넘으면 `AI_FAILED`다.
- 프롬프트를 goal-scenario-v5로 바꿔 시나리오당 칠백~천 자 안팎으로 목표 금액·기한에 비춘 이유, 상품별 비율·역할·근거, 다른 시나리오와의 차이, 기한이 다가올 때 주의할 점, 어떤 사람에게 맞는지를 담게 한다.
- 근거를 인용할 수 있게 AI에게 보낸 유형별 통계와 자료 기간("지난 60개월")을 허용한다(사용자 결정). 서버가 대조할 수 있는 값만 허용한다는 원칙은 그대로이고, 소수 첫째·둘째 자리로 반올림해 같은 값만 통과한다. 정수 표기까지 허용하면 지어낸 "연 7% 수익"이 통계와 우연히 맞아 통과하므로 허용하지 않는다. 값만 맞으면 "기대 수익 4.56%"처럼 변동폭을 수익으로 쓸 수 있어, 같은 문장에서 가장 가까운 종류 단어("평균"·"변동"·"하락")의 값이어야 하고 수익 예상을 뜻하는 말이 없어야 통과한다(사용자 결정). 어느 상품의 값인지는 구분하지 못한다. 거절이 잦으면 AI가 자리표시자를 쓰고 서버가 수치를 채우는 방식을 검토한다. 과거 값임을 밝히고 수익 예상처럼 쓰지 않도록 프롬프트로 안내한다.
- 길어진 응답에 맞춰 토큰 상한을 1200에서 4000으로, 호출 제한 시간을 25초에서 60초로, nginx `proxy_read_timeout`을 30초에서 70초로 늘린다. 서비스 전체 하루 300회 상한은 그대로라 호출 수는 늘지 않지만 호출당 비용은 늘어난다.
- 뒤쪽 문장이 걸려도 원인이 보이도록 로그에 남기는 걸린 칸의 문구 상한을 300자에서 2000자로 늘린다.
- 월 납입액·달성 확률은 AI가 비중을 낸 뒤 서버가 계산하므로 해설에 넣지 않는다. 자동 재시도는 실제 호출 결과를 본 뒤 정한다.

## 11-06 AI 해설 깊이와 문장 단위 처리(사용자, #286)

- #279 배포 후 운영 로그의 해설이 300자 안팎이었고 통계 인용과 상품별 근거가 없었다. "나머지 70%"처럼 비중을 더한 사실인 숫자 때문에 제안 전체가 데모로 바뀌었다(로그에 비중이 없어 문구로 추론). 프롬프트로 금지해도 AI가 썼다.
- 비중의 합도 서버가 계산해 대조할 수 있으므로 합쳤다는 말과 함께 쓰면 허용한다. 문장 앞쪽이나 숫자 바로 뒤에 수익·확률·예상을 뜻하는 말이 있거나 숫자 앞이 "연"이면 막는다("예상 수익은 모두 합쳐 연 80%"가 비중의 합과 우연히 맞아 통과하지 않게). 멀쩡한 문장도 막힐 수 있지만 그 문장만 지워진다.
- 해설을 필수 칸 네 개로 받아 서버가 문단으로 합친다. 글자 수 안내만으로는 길이와 내용을 지키지 않았기 때문이다. 한 칸이라도 비면 제안 전체를 버린다. 화면이 받는 `explanation`과 계약은 그대로다.
- 위 "하나라도 어기면 제안 전체를 버린다"를 해설의 숫자·보장 표현에 한해 조정한다: 걸린 문장만 지우고 나머지를 쓴다(사용자 결정). 비중은 맞는데 문장 하나 때문에 데모로 바뀌는 일을 줄이고, 걸린 문장은 화면에 내보내지 않는다. 다 지워지면 제안 전체를 버린다. 문장이 빠져 글의 흐름이 어색할 수 있고, 지운 문장은 로그로 추적한다.
- 자동 재시도는 비용과 대기 시간이 두 배까지 늘 수 있어 이번에도 넣지 않는다.
