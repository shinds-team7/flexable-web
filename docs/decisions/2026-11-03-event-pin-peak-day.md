# 사건 핀은 기간 중 가장 크게 움직인 날에 꽂는다

- 날짜: 2026-11-03 · 제안: 개발(rhkrqkq) · 결정: 사용자(11-03, 여러 날 사건 핀이 더 작게 움직인 날에 꽂힌다는 지적 뒤 서버 계산 방식으로 진행) · 관련: Issue #, PR #
- 상태: 제안. 이 기록과 구현을 담은 PR이 병합되면 결정됨으로 본다.
- 영향: 웹 백엔드(`market.EventDetector`·`market_events`·사건 핀 응답), API 계약(`PriceEvents.items.peakDate`), 웹 프론트(투자 인사이트 차트 핀). 탐지 규칙·`detector_version`·개인정보 처리 항목은 바뀌지 않는다. 앱·시연은 범위 밖이다.
- 기준: [03 C-8](../product/03-architecture.md) "표시"·"검증", [투자 인사이트 개편 결정](2026-10-26-invest-insight-redesign.md)

## 배경

투자 인사이트 차트는 사건 핀을 사건 **시작일**에 꽂았다. 합친 사건(3영업일 안)과 5일 사건은 시작일이 가장 크게 움직인 날이 아닐 수 있어, 차트에서 더 크게 움직인 날 대신 작게 움직인 날에 핀이 보였다. 예: 2024-08 시장 사건(08-02~08-05)의 핀이 −4.02%인 08-02에 꽂히고 −9.18%인 08-05에는 없었다.

로컬 평가 DB(8년, 89종목)로 재면 여러 날 종목 사건 324건 중 192건(59%)이 이 경우였다. C-8의 검증 기준("누가 봐도 큰 날"이 잡히는지)에 비춰 화면이 사건을 잘못 가리키는 문제로 본다.

## 결정

1. **핀 날짜(`peakDate`)는 사건 기간(시작일~마지막 날) 중 하루 등락 절댓값이 가장 큰 날이다.** 하루 등락은 전날 종가 대비(수정주가)다. 같은 값이면 앞선 날이다. 1일 사건이면 시작일과 같다.
2. 시장 사건도 같은 규칙을 시장 대용 종목(기본 069500)의 종가로 쓴다.
3. **계산은 서버가 한다**(ADR-3). 탐지기가 사건마다 `peakDate`를 내고 `market_events.peak_date`에 저장하며, `GET /market/instruments/{id}/events`의 `items[].peakDate`로 준다. 화면은 등락을 계산하지 않는다.
4. 이 열을 더하기 전에 저장한 사건은 `peakDate`가 null이고, 화면은 그때 시작일에 핀을 꽂는다. worker가 사건을 다시 탐지하면 채워진다(시세 수집 뒤 매번 탐지).
5. **어떤 사건을 찾는지는 그대로다.** 기간·방향·수익률·z·점수·연도 순위는 바뀌지 않으므로 `detector_version`은 `v1-2026-10`을 유지한다.
6. 툴팁·사건 목록의 기간 표기(시작일~마지막 날)와 기간 수익률은 그대로다. 바뀌는 것은 핀의 위치뿐이다.

## 이유

- 사용자는 차트를 절대 등락폭으로 읽는다. 핀이 기간 안에서 가장 크게 움직인 날에 있어야 "무슨 일이 있었나"와 선의 모양이 맞는다.
- 핀 날짜를 화면이 종가로 고르면 등락을 화면이 계산하게 된다. 서버가 같은 종가로 한 번 정해 주면 상세·목록·차트가 같은 날을 가리킨다.
- 같은 사건의 표시 정보라 탐지 버전을 올리지 않는다. 사건 id·근거·AI 개요를 그대로 지킨다.

## 하지 않은 것

- 같은 해에 사건이 덮지 않은 더 크게 움직인 날이 있는 사건(로컬 평가 DB 기준 약 48%)은 v1이 종목 자신의 평소 흔들림과 시장 영향을 뺀 z로 찾는 정의 때문이다. 이를 줄이려면 C-8 탐지 정의를 바꿔야 하므로 별도로 정한다.
- 시뮬레이션 실행 결과(`POST /simulations/run`의 `events`)와 사건 상세(`EventDetail`)에는 `peakDate`를 더하지 않았다. 지금 핀을 그리는 곳은 투자 인사이트 차트뿐이다.
