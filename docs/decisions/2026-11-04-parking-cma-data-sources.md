# 파킹·CMA 공식 공개 자료의 적재 경로 재검토

- 날짜: 2026-11-04 · 제안: 개발 · 검토: 팀 리드 · 관련: #143, #144, #145, #148
- 상태: **조사 결과 및 변경 제안. 승인·병합 전에는 기존 11-01 결정을 대체하지 않는다.**
- 영향: 웹 프론트(금리 고지·조건 표시), 웹 백엔드(수집·저장·계산), 향후 API 계약. 앱·시연 변경 없음.
- 기준: [기존 결정](2026-10-31-parking-cma.md), [PRD](../PRD.md), [정책 §6·§7](../policies.md), [API 계약](../contracts/web-api.yaml), #144·#145·#148 본문 및 댓글(11-04 확인).

## 현재 구현과 이번 범위

정기예금은 `ingest.FinlifeClient.fetchAllDeposits` → `SavingsSnapshotJob.syncDeposits` → `deposit.DepositCatalogService.replaceAll` → `/deposit/*` 경로가 구현돼 있다. 매일 10:00(KST), 시작 시 빈 DB에 수집하며 실패하면 기존 데이터를 유지한다. 운영 키·실제 수집 성공·운영 DB의 최신성은 이번에 확인하지 않았다. `.env`·운영 DB는 접근하지 않는다.

파킹·CMA는 예시 데이터 분기가 있고, `/parking/*`·`/cma/*` 계약과 서버 구현은 없다. `SavingsSector`는 `BANK`·`SAVINGS_BANK`뿐이다. F7 목표 시나리오의 CMA 예시 금리·계산은 별도 정책이며 이 작업에서 바꾸지 않는다.

#148의 운영자 입력 표·월 지급 단리 계획과 일부 HANDOFF 내용은 현재 구현 및 11-01 결정과 다르다. 11-01 결정 ③(운영자 입력 표 제외, 출처 확정 전 수집 코드 금지)과 ⑤(파킹 계산·CMA 재투자 미정)를 우선한다. 이 문서는 수집 코드·DB·계약·계산 정책을 추가하지 않는다.

### 다른 서비스의 공개된 근거

[네이버페이 예적금 FAQ 13359](https://help.pay.naver.com/faq/content.help?faqId=13359)는 금융회사 홈페이지 공개 내용을 예금·적금·파킹 금리의 기반으로 설명한다. [CMA FAQ 13360](https://help.pay.naver.com/faq/content.help?faqId=13360)는 증권사 공개 정보를 기반으로 약정수익률이 있는 RP형·발행어음형·종금형 일부를 제공하며 1일 기준으로 비교한다고 설명한다.

따라서 통합 API가 비교 서비스의 유일한 경로는 아니다. 다만 FAQ는 네이버의 크롤링 방식·계약·제휴 여부를 공개하지 않으므로 우리 서비스의 이용 허가 근거는 아니다.

### 조사 도구의 한계

GitHub CLI로 #144·#145·#148을 읽었고, 추가 출처 승인 기록은 없었다. Postman/Orbit 검색에서 적합한 상품 금리 API를 찾지 못했으며 이는 부재의 증명이 아니다. 설치된 Postman CLI 1.73.0은 스킬의 `postman status`를 지원하지 않아 해당 상태 검증·Context Graph 조사는 수행하지 않았다. 외부 기관 문의는 발송하지 않았다.

## 승인 후 적재 설계안

`출처 등록 → 허용된 원본 취득 → 형식·조건 검증 → 출처별 DB 스냅샷 반영 → 서버 조회·계산`

아래 이름은 저장 구조 검토용이며 공개 API 필드나 Flyway 테이블 확정안이 아니다.

| 묶음 | 보관할 내용 |
|---|---|
| 출처 | 기관, 공식 URL, 제공 방식, 이용 조건 URL/확인 근거·확인일, 허용 범위·주기. 비밀 값·문의자 개인정보는 저장소에 넣지 않음 |
| 원본·수집 실행 | 취득 시각(`fetchedAt`), 원본 해시, 형식/파서 버전, 성공·실패, 검증 오류. 원본 보관 범위·기간은 이용 조건 확인 후 결정 |
| 상품 | 출처의 안정된 상품 식별자, 회사, 유형, 가입 대상·한도, 보호 여부와 확인 근거. 이름만으로 병합하지 않음 |
| 금리·조건 | 금액 구간·기간 구간, 경계 포함 여부, 구간별 적용/전체 잔액 적용 방식, 우대조건 원문, 약정/실적 구분, 실적 측정 기간, 지급·재투자 주기 |
| 시간 | 공시 기준일(`sourceAsOf`), 적용 시작일(`effectiveFrom`), 취득 시각, 검증 시각(`verifiedAt`)을 구분. 출처에 없는 적용일은 null로 남김 |

금액·금리·세금 계산은 서버에서 한다. 최고금리 적용 한도 하나만으로 한도 초과분 금리를 만들어 내지 않는다. 공시가 복잡한 조건을 표현하지 못하면 계산 대상으로 자동 공개하지 않고 검증 대기시킨다. 미지원 상품을 숨기는 기준과 목록에만 표시하는 기준은 계약·정책 PR에서 정한다.

수집 결과가 비었거나 파싱·필수 필드·구간 검증이 실패하면 해당 출처의 기존 정상 스냅샷을 유지한다. 다른 출처까지 지우는 전역 교체는 하지 않는다. 부분 조회를 전체 목록으로 오인해 상품을 삭제하지 않으며, 변경 이력·판매 중단 판정·오래된 데이터 처리 기준을 별도로 정한다. 출처가 오래 갱신되지 않았는데 방금 수집한 날짜를 최신 금리 기준일로 표시하지 않는다.

## 다음 작업과 완료 조건

1. **정기예금 기존 경로 검증**: 기존 정책·계약 테스트, 로컬 설정에서 수집 성공·실패 시 데이터 유지·필터·상세·비교 확인. 운영 접근 없이 확인 가능한 범위부터 진행하고 키 없는 실제 호출은 수행하지 않음.
2. **공식 제공 조건 확보**: 저축은행중앙회부터 파일 표본·필드 설명·자동 취득/재사용 조건·갱신 기준 확보. 은행연합회와 CMA 후보 증권사는 병행 문의 준비. 외부 문의 발송은 별도 사용자 지시 후 진행.
3. **결정·계약·정책 PR**: 위 변경 제안과 미정 규칙을 리드가 확정. `/parking/*`·`/cma/*` 계약 및 실제 입력→기대값 fixture 작성, `gen:api`·소비자 타입 영향 확인. 이 단계가 승인·병합되기 전 구현 착수하지 않음(#144·#145).
4. **허용된 출처 하나로 구현**: 취득·파서·Flyway·스냅샷·조회·계산을 연결. 출처별 실패·빈 응답·구간 경계·기준일 누락을 검증하고 `ContractTest`·`tests/policy` 통과.
5. **화면 전환**: 금액·회사·유형 필터, 정렬, 상세·비교, 고지, 1280/390px·라이트/다크·키보드 확인. 실제 연동 확인 뒤 해당 종류의 예시 분기 제거. 운영 환경 변수는 사람이 설정.

#144·#145·#148은 전체 완료 전 닫지 않는다. 아직 허용 출처·계산·계약이 확정되지 않았으므로 현재 파킹·CMA의 `isSample` 표시를 유지한다.

### 저축은행중앙회·은행연합회
