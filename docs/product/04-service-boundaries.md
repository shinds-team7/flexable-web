# 앱·웹 서비스 경계 (2026-10-20 재작성)

> 사용자 결정(2026-10-20). **이 문서가 `03-architecture.md` ADR-1(공유 백엔드·모듈러 모놀리스)과 이 문서의 이전 판(공유 API)보다 우선한다.** 구조 결정이며 구현 완료 기록이 아니다. 웹 백엔드는 웹 계정(§4)과 §5 앱 연동하기(웹 쪽 백엔드·내 정보 화면, 2026-10-20)까지 구현됐다([`backend/README.md`](../../backend/README.md)). 앱 실서버와의 통합 확인은 아직이다(§10).

## 1. 한 줄 요약

웹과 앱은 **서버·DB·계정이 각각 따로**다. 웹 사용자가 원하면 [앱 연동하기]로 자기 앱 계정을 연결하고, 연결된 동안만 앱의 회원 정보와 시드머니를 읽어 온다.

## 2. 왜 분리하나

- 웹은 앱과 별개로 **아카데미 내부 폐쇄망 VM**에 띄운다. 사양은 주최 측이 맞춰 주고, **VM에서 인터넷(project2 API)으로 나가는 연결은 가능**하다.
- 시세 수집·시뮬레이션 부하가 앱 API에 영향을 주면 안 되고, 웹 배포는 앱과 독립적이어야 한다.
- 앱을 쓰지 않는 사람도 웹만 가입해서 쓸 수 있어야 한다.

## 3. 무엇이 어디에 있나

| 영역 | 코드 | 실행 위치 | DB |
|---|---|---|---|
| 웹 화면 | flexable-web `src/` | 폐쇄망 VM(정적 파일) | — |
| 웹 백엔드 | flexable-web `backend/` | 폐쇄망 VM | 웹 전용 DB(엔진·호스팅·용량·백업 구성 미정) |
| 앱 | project2 `frontend/` | 휴대폰·Vercel | — |
| 앱 백엔드 | project2 `backend/` | 기존 운영 서버 | 앱 DB(기존) |
| 앱 시연 | flexable-web `mobile-demo/` | 웹 `/m` | 예시 데이터만 |

```text
브라우저 ──▶ 폐쇄망 VM: 프록시 ─┬─ 웹 정적 파일
                               └─ /api ─▶ 웹 백엔드 ─▶ 웹 DB
                                              │ applink (서버끼리, HTTPS)
                                              ▼
                                        project2 /internal/v1/... ─▶ 앱 DB
```

- 브라우저는 **웹 백엔드만** 호출한다. 브라우저가 project2를 직접 부르지 않는다.
- 웹 백엔드에서 project2를 부르는 코드는 `applink` 패키지에만 둔다.

## 4. 계정

| | 웹 | 앱 |
|---|---|---|
| 가입·로그인 | 웹 DB의 웹 계정. 이메일·비밀번호와 카카오·Google(2026-10-20 사용자 결정, project2와 같은 PKCE 흐름). 소셜로 들어와도 웹 DB에만 계정이 생긴다 | 기존 project2 계정 |
| 토큰 | 웹 백엔드가 자체 비밀키(`WEB_JWT_SECRET`, 앱 키와 다른 값)로 발급. `iss=flexable-web`을 넣고 검사해 앱 토큰과 섞지 않는다. 폐기는 웹 `tokenVersion` | 기존 JWT·tokenVersion |
| 로그아웃 | 웹 세션만 끝난다(이 회원의 모든 기기 웹 토큰) | 앱 세션만 끝난다. **웹과의 연동은 유지된다** |
| 탈퇴 | 비밀번호 확인 → 웹 데이터·웹 연동 삭제 + 커밋 뒤 앱 서버에 해제 요청 1회(앱 서버 장애로 실패해도 탈퇴는 끝나고, 앱의 연동 목록에 남은 것은 앱에서 지운다) | 앱 데이터 삭제 + 그 계정의 연동 전부 삭제 → 웹은 다음 조회 때 "연동 해제됨"으로 바꾼다 |

웹 계정 API(2026-10-20 구현): `POST /api/v1/auth/signup`·`/login`·`/logout`, `GET`·`DELETE /api/v1/me`, `GET`·`PATCH /api/v1/me/settings`, `GET /api/v1/auth/oauth/providers`·`/{provider}/start`·`/{provider}/callback`, `POST /api/v1/auth/oauth/exchange`. 요청·응답은 [`backend/README.md`](../../backend/README.md) "API".

같은 사람이 웹과 앱에 같은 이메일로 가입해도 **계정이 자동으로 합쳐지지 않는다.** 이메일이 같다는 것만으로는 앱 정보를 넘기지 않는다(남의 이메일로 웹에 가입하는 경우를 막기 위함). 연동은 아래 코드 절차로만 한다. 웹 이메일과 앱 이메일이 달라도 연동할 수 있다.

웹은 "이 이메일로 가입된 앱 계정이 있는지"를 화면에 알려 주지 않는다(가입 여부 노출 방지). [앱 연동하기] 버튼은 항상 보인다.

## 5. 앱 연동하기

### 5-1. 흐름

1. **앱**: 설정 > [웹 연동 코드 받기]. 앱이 `POST /api/v1/me/web-link-codes`(사용자 JWT)로 코드를 받는다. 코드는 8자리, **10분 유효, 한 번만 사용**. project2는 해시만 저장한다.
2. **웹**: 로그인한 사용자가 [앱 연동하기] → 코드 입력 → 웹 백엔드 `POST /api/v1/app-link { code }`. 지금은 내 정보 화면에서 시작한다(가입 직후 화면의 진입점은 §10).
3. **웹 백엔드 → project2**: `POST /internal/v1/web-links { code }`(서비스 인증). project2는 코드를 확인하고 연동 레코드를 만든 뒤 `{ linkId, profile: { email, provider } }`를 돌려준다(앱에는 닉네임이 없다). `linkId`는 추측할 수 없는 임의 값이다.
4. **웹 백엔드**: `app_links`에 (웹 사용자, 암호화한 `linkId`, 연동 시각)을 저장하고 화면에 "앱 계정 ○○○과 연동됨"을 표시한다. **웹 회원당 연동은 하나**이고, 이미 연동돼 있으면 409 `APP_LINK_EXISTS`(해제 후 다시 연동). 앱에서 연동을 만든 뒤 웹 저장이 실패하면 앱 서버에 해제를 요청해 되돌린다. 요청을 보낸 뒤 응답을 못 받으면 코드가 쓰였는지 알 수 없으므로 다시 보내지 않고 "앱의 연동 목록 확인 후 새 코드"로 안내한다(502 `APP_LINK_RESULT_UNKNOWN`).

이후 조회는 `linkId`와 서비스 인증으로만 한다. 앱 로그인 상태와는 관계없다.

### 5-2. 연동으로 받을 수 있는 정보 (최소 범위)

| 정보 | project2 API(초안) | 웹 쪽 저장 |
|---|---|---|
| 앱 회원 정보: 이메일·로그인 방법(`email`은 소셜 계정이면 null 가능, `provider` = email·kakao·google) | `GET /internal/v1/web-links/{linkId}/profile` | 화면 표시용 최소값만 |
| 시드머니(앱에서 확정한 값): `total`(모아둔 돈 + 반영한 돈), `base`(모아둔 돈), `monthlyGoal`(매달 저축할 돈), `lastEntry`(마지막 반영: 주기 끝 날짜·방법·금액), `updatedAt` | `GET /internal/v1/web-links/{linkId}/seed-money`. 앱 예산 설정 전이면 404 `BUDGET_NOT_SET` | 마지막 값과 받은 시각(`app_links`, 연동과 함께 삭제) |

거래 목록·카테고리 같은 원본 기록은 넘기지 않는다. 금액 계산은 project2가 하고 웹은 다시 계산하지 않는다. 시드머니는 앱에서 사용자가 수입일 전날 확정한 값이라(2026-10-20 결정, [decisions](decisions.md) ②) 수입일 즈음에만 바뀐다. 반영 대기·주기별 기록은 넘기지 않는다. 정확한 응답 형식은 [앱 API 문서](https://github.com/shinds-team7/flexable-app/blob/main/docs/API.md) "웹사이트 연동"·"시드머니". 정보 범위를 넓힐 때는 이 표부터 고친다.

### 5-3. 해제·오류

- **웹에서 해제**: `DELETE /api/v1/app-link` → 웹 백엔드가 `DELETE /internal/v1/web-links/{linkId}` 호출 → 웹에 저장된 앱 정보 삭제.
- **앱에서 해제**: 앱 설정에 연동 목록과 [해제]를 둔다(초안). 해제되거나 앱이 탈퇴되면 project2는 `404 LINK_NOT_FOUND`를 돌려주고, 웹은 연동을 끊고 저장된 앱 정보를 지운다.
- **project2 장애·시간 초과**: 웹은 마지막으로 받은 값을 "○월 ○일 ○시 기준"과 함께 보여 준다. 화면 전체를 막지 않는다. `LINK_NOT_FOUND` 말고는(다른 404·5xx·시간 초과·서비스 키 오류) 연동을 지우지 않는다. 웹 해제 중 장애면 해제를 실패로 돌려주고 연동을 남긴다.
- 코드 입력 실패는 웹 사용자당 10분에 5회(웹), project2 서비스 전체 10분에 30회(앱)로 제한한다.
- 앱 로그아웃은 연동을 해제하지 않는다.

### 5-4. 서버 간 인증

- 경로는 `/internal/v1/...`로 사용자 API(`/api/v1/...`)와 분리한다. project2는 이 경로를 사용자 JWT로 열지 않는다.
- 웹 백엔드는 서비스 키 헤더로 인증한다. 키는 양쪽 서버 환경변수에만 두고 저장소·문서에 적지 않는다. project2 프록시에서 폐쇄망 VM의 나가는 IP만 허용하는 것을 함께 검토한다.
- 키 교체 시 두 키를 잠시 함께 허용한다(무중단 교체).

## 6. 데이터 소유

| 테이블(초안) | DB | 소유 |
|---|---|---|
| 웹 회원(이메일·동의 시각)·웹 설정: `users`, `user_settings` | 웹 | 웹 `user` |
| 로그인 수단(비밀번호 해시·토큰 버전): `user_credentials` | 웹 | 웹 `auth` |
| `app_links`(웹 사용자 ↔ 암호화한 `linkId`, 앱에서 마지막으로 받은 회원 정보·시드머니) | 웹 | 웹 `applink` |
| 웹에서 입력·고친 시드머니 | 웹 | 웹 `seedmoney`(앱 값은 `applink` 공개 서비스로 읽는다) |
| 시세·사건·적금·소식·시뮬레이션·결제·목표 | 웹 | 웹 각 패키지 |
| 연동 코드(해시)·연동 레코드 | 앱 | project2 (새 패키지, 이름은 구현 시 확정) |
| 사용자·거래·예산 | 앱 | project2 기존 패키지 |

- 웹 DB는 앱 테이블을 복제하지 않는다. 두 DB 사이에 외래 키는 없다.
- 회원 정보와 로그인 수단을 나눈 이유: `auth → user` 의존 방향을 지키면서 `user`가 auth를 모르게 하기 위해서다. 탈퇴 때 다른 패키지의 데이터는 `user.UserWithdrawalListener` 구현으로 지운다.
- 앱에서 받은 마지막 값은 해제·`LINK_NOT_FOUND` 때 함께 지워야 하므로 `applink`가 가진다(2026-10-20 구현 시 결정. `applink`는 `seedmoney`에 의존할 수 없다).
- 각 DB의 Flyway 이력은 따로 관리한다. project2 기존 마이그레이션 규칙(추가만)은 그대로다.

## 7. 웹 API 경로

웹 백엔드는 자기 서버이므로 `/api/v1/...`를 그대로 쓴다. 이전 판의 `/api/v1/web/...` 접두어는 쓰지 않는다. `03-architecture.md` 8장의 경로는 웹 백엔드 기준 `/api/v1`로 읽는다. 시드머니는 앱 API가 아니라 웹 백엔드의 `/api/v1/me/seed-money`가 된다(연동이 없으면 웹에서 입력한 값만).

## 8. 수집 작업(worker)

적금·시세·종목 뉴스·AI 해석의 최초 적재·정기 갱신은 [웹 데이터 저장·자동 갱신 계획](05-data-refresh.md)을 따른다. 웹 DB 구성과 자동 갱신의 해커톤 포함 여부는 미정이며, 이 문서의 분리 원칙만으로 DB 제품·설치 위치를 확정하지 않는다.

웹 백엔드 jar를 `worker` 프로필로 한 번 더 띄워 수집·사전 생성만 한다(HTTP 없음, `spring.main.web-application-type=none`). VM 하나에서 같이 돌므로 컨테이너 자원 제한·DB 연결 풀 상한·중복 실행 방지·재시도를 함께 설계한다. 외부 API 호출은 worker만 한다. 예외: 소셜 로그인 공급자(카카오·Google) 호출은 로그인 요청 중에 api가 한다.

## 9. 작업 나누기

| 작업 | 저장소 |
|---|---|
| 웹 계정·연동 화면·웹 백엔드 전체 | flexable-web |
| 연동 코드 발급 API, `/internal/v1/web-links/*`, 서비스 키 검증, 앱 탈퇴 시 연동 삭제, 시드머니(모아둔 돈·반영) | project2 `backend/` (PR #82·#83) |
| 앱 설정의 [웹 연동 코드 받기]·연동 목록 화면 | project2 `frontend/` (JS 변경이라 EAS 원격 업데이트로 반영 가능, 미구현) |
| 온보딩 '모아둔 돈'·'매달 저축할 돈', 수입일 전날 알림·반영 창 | project2 `frontend/` (PR #83, 기기 알림 때문에 앱 1.3.0 새 빌드) |

연동 API는 두 저장소에 연계 PR로 올리고, 계약은 project2 `docs/API.md`에 적는다.

## 10. 아직 정하지 않은 것

- 웹 DB 엔진·호스팅·용량·백업·복원 방식
- 데이터 자동 갱신의 도입 일정·제공처·실행 시각([상세](05-data-refresh.md#7-구현-전-결정할-것과-검증-기준))
- 웹 소셜 로그인에 쓸 공급자 앱. 같은 카카오·Google 앱에 웹 콜백을 더해도 동작한다(조건은 [HANDOFF](HANDOFF.md) "웹 백엔드 운영 전환"). 웹 도메인을 붙일 수 있는지에 따라 Google 사용 여부가 갈린다
- 시연 대본의 '거래 1건 → 웹 숫자 변화' 대체 장면(시드머니가 수입일 전날에만 바뀌므로)
- 앱 쪽 연동 목록 화면의 위치·문구
- 웹 회원당 연동 하나·교체 없음(이미 연동이면 409)은 구현 기본값이다. 다른 앱 계정으로 바로 바꾸는 흐름이 필요한지 결정
- 가입 직후 화면에서 [앱 연동하기]로 들어가는 진입점(§5-1). 지금은 내 정보에만 있다
- 홈·상단 바의 시드머니(`src/data/home.ts` 예시 값)를 연동한 앱 시드머니로 바꾸는 작업(`seedmoney` 패키지·`GET /api/v1/me/seed-money`)
- 개인정보처리방침에 웹이 앱에서 받는 항목(앱 이메일·로그인 방법·확정 시드머니)과 보관·삭제 시점을 넣을지와 시행일. 공개 전에 확인
- 앱 실서버 통합 확인: 앱 1.3.0 출시·앱 화면 원격 업데이트 뒤 앱 코드 발급 → 웹 연동 → 시드머니 조회 → 양쪽 해제 반영을 실기기로
- 폐쇄망 VM의 나가는 IP 고정 여부(IP 허용 목록 사용 가능성)
