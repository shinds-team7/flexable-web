# 웹 데이터 저장·자동 갱신 계획

기준일: 2026-10-20. 사용자 제안과 후속 논의에서 합의한 설계다. 구현·배포 완료 기록이 아니다.

이 문서는 적금·시세·종목 뉴스·AI 해석의 저장·갱신에 관해 이전 계획보다 우선한다. 앱·웹 분리 원칙은 [서비스 경계](04-service-boundaries.md)를 따른다. 10-20 작성 당시 웹 DB 구성은 미정이었다. 지금 VM은 MySQL 8.4 컨테이너를 쓰고(아래 §0), 11-18 VM 종료 뒤 AWS 구성은 정하지 않았다.

## 1. 합의한 방향과 적용 시점

- 웹 서비스가 자기 DB에 적금 상품·금리 조건, 과거 시세, 종목별 사건·뉴스, AI 해석을 저장한다. 앱 DB에 저장하거나 앱 API가 수집을 맡지 않는다.
- 처음에는 필요한 전체 범위를 적재하고, 이후 정해진 시각에 스케줄러로 갱신한다. 화면 요청마다 외부 API를 호출하지 않고 웹 API가 저장된 데이터를 조회한다.
- 외부 데이터 수집·AI 사전 생성은 웹 worker가 맡는다. API 프로세스에서는 수집 스케줄러를 켜지 않는다(api의 정기 작업은 앱 연동 확인·목표 안내 사용량 정리뿐이고 데이터 수집이 아니다).
- 등록된 종목의 신규 뉴스를 수집해 사건 후보를 만들고, 관련성·중요도·중복 여부를 확인해 차트 핀으로 제공한다. AI 해석은 초안으로 저장하고 검수·승인 후 공개한다.
- **자동 갱신을 이번 개발·해커톤에 포함할지는 미정**이다. 별도 일정 결정 전에는 [기존 확정 17](decisions.md)의 시연 종목 10~15개·3년 일봉 1회 적재 범위를 유지한다. 이번 합의만으로 매일 갱신이 해커톤 Must가 되지는 않는다. (10-24 현재: 시세는 이미 상위 100종목 자동 갱신으로 구현됐다(§0). 적금·뉴스 자동 갱신은 미정 그대로다.)

## 2. 적금 비교 데이터

### 최초 적재

대상 API에서 제공하는 권역·페이지를 순회해 비교 대상 상품 전체를 받는다. 여기서 전체는 해당 API의 제공 범위이며, 시장의 모든 상품을 포함한다고 가정하지 않는다. 현재 문서의 finlife는 후보 소스이며 실제 응답·호출 제한·이용 조건을 확인한 뒤 연결한다.

API가 제공하는 페이지 단위와 DB 저장 단위는 별개다. 약 3,000건은 설계 논의를 위한 예시이며 실제 상품 수나 API의 1회 반환 건수가 아니다. API의 최대 페이지 크기를 확인하고, DB 저장도 제한된 건수씩 처리한다. 페이지 크기·저장 건수·동시 호출 수는 응답 크기와 호출 제한을 측정해 정한다.

### 저장할 정보

| 구분 | 내용 |
|---|---|
| 상품 | 제공처·금융회사·상품 식별자, 상품명, 가입 대상·제한, 한도, 우대조건 원문, 판매 상태 |
| 금리 옵션 | 기간·적립방식·이자 계산 방식별 기본금리·최고금리와 제공처의 옵션 식별값 |
| 변경 이력 | 상품 조건·금리 옵션의 변경 전후 값, 관측 시각, 제공처가 명시한 적용 시점 |
| 기준 정보 | 원문 링크·출처, 공시 기준일 또는 기준월, 마지막 확인 시각, 수집 실행 ID |

상품은 제공처·금융회사·상품 식별자로, 옵션은 해당 상품과 옵션 구분값으로 중복을 막는다. 실제 키는 응답을 확인한 뒤 정한다. 현재 값만 덮어쓰지 않고 조건 변경 이력을 남긴다. **수집한 날을 금리가 실제 적용된 날로 간주하지 않는다.** 이력이 없던 과거 시점의 상품 금리는 복원했다고 표시하지 않는다. 과거 평균 적금 비교는 기존 ECOS 계획과 구분한다.

### 매일 갱신

1. 예정 시각에 대상 전체를 페이지별로 조회한다. 변경분 조회를 지원하면 그 방식을 검토하되, 지원한다고 가정하지 않는다.
2. 수집 결과를 실행 ID로 구분해 임시 보관하고 상품·옵션의 연결과 누락을 검증한다.
3. 검증에 성공한 결과를 현재 조회 대상으로 전환하고 변경 이력을 남긴다. 저장은 나눠 처리해도 조회 화면에는 완성된 수집 결과를 제공한다.
4. 전체 수집이 성공한 범위에서만 목록에서 사라진 상품을 판매 종료 후보로 확인한다. 제공처의 종료 표시·누락 의미를 확인해 상태를 결정한다.

일부 페이지 실패·호출 한도 초과·비정상 빈 응답 때는 기존 상품을 일괄 종료하거나 삭제하지 않는다. 마지막 성공 결과를 유지하고 갱신 지연 상태를 남긴다. 화면에는 공시 기준일과 마지막 갱신 시각을 구분해 표시한다.

## 3. 투자 시뮬레이션용 시세

최초 적재는 선택한 종목과 기간을 대상으로 날짜·페이지를 나눠 수행한다. 이후에는 제공처에 실제 공개된 최신 거래일을 기준으로 추가·정정분을 갱신한다. 매일 전체 과거 데이터를 다시 받지 않는다.

- 시세는 종목·거래일을 고유 기준으로 저장한다. 가격·거래량, 출처, 시세 기준일, 수집 시각과 데이터 버전을 남긴다.
- API의 갱신 시각·지연·거래소 휴장일을 확인해 작업 시각을 정한다. 매일 실행해도 새 거래일 데이터가 없으면 정상 종료할 수 있다. 휴장일을 장애로 처리하지 않는다.
- 최근 일정 구간을 다시 조회해 지연 등록·정정을 반영한다. 재조회 기간은 제공처 특성에 맞춰 정하고, 과거 구간 재수집도 가능하게 한다.
- 분할·병합·배당과 수정주가 제공 여부를 확인한다. 확인 전 임의 보정하지 않고 기존 시연 종목 검수 규칙을 유지한다.
- 가격이 정정되면 관련 사건 수치·시뮬레이션 결과·설명의 재검증 대상을 표시한다. 과거 계산 결과에 사용한 기준일·데이터 버전을 추적할 수 있게 한다.

## 4. 종목 뉴스와 사건 핀

### 수집 범위와 제공처

등록된 종목을 대상으로 신규 뉴스를 수집한다. 수집 대상 종목 목록은 화면의 노출 대상과 구분해 관리한다. 최초 시연 종목 수나 전체 시장 확대 범위를 이번 결정으로 늘리지는 않는다.

**최신 뉴스 수집과 과거 뉴스 확보는 별도 작업**이다. 과거 조회 가능 기간·페이지 상한·수집 가능한 건수를 확인한 뒤 초기 적재 범위를 정한다. 최근 검색 API만으로 과거 전체 뉴스가 확보된다고 가정하지 않는다.

뉴스 제공처는 아직 정하지 않았다. 저장·화면 표시·AI 입력이 허용되는 데이터와 필드를 확인한 뒤 연결한다. 본문 전체 저장을 기본값으로 두지 않는다. 허용 범위 안에서 제공처 ID, 제목, 언론사, 원문 링크, 발행·수정 시각, 수집 시각, 연결 종목을 저장한다. AI 입력 허용이 확인되지 않은 내용은 해석 생성에 보내지 않는다. 기존의 수동 기사 메타데이터 등록은 자동 수집 소스가 준비될 때까지 사용할 수 있다.

### 핀 생성

`뉴스 수집 → 중복 제거 → 종목 연결 → 사건 후보 → 관련성·중요도 확인 → 공개 핀`

- 제공처·기사 ID 또는 정규화한 원문 URL로 재수집 중복을 막는다. 같은 사건의 여러 보도는 한 사건에 근거로 묶을 수 있게 한다.
- 회사명 검색만으로 종목 연결을 확정하지 않는다. 동명이인·계열사·상품명 혼동을 확인한다.
- 모든 새 기사를 핀으로 공개하지 않는다. 중요도 기준·일별 노출 개수는 미정이며, 가까운 날짜의 핀 묶음과 기존 차트 표시 규칙을 함께 적용한다.
- 뉴스 발행 시각, 실제 사건 시각(확인 가능한 경우), 수집 시각, 차트에 연결한 거래일을 구분한다. 장 마감 후·휴장일 기사의 연결 규칙을 정하고, 수집한 날짜에 일괄 배치하지 않는다.
- 뉴스가 가격 변동의 원인이라는 사실은 자동으로 확정하지 않는다. 기사 정정·삭제 시 연결된 사건과 설명을 재검토할 수 있게 한다.

## 5. AI 해석

`허용된 근거·서버 계산 수치 → AI 초안(DRAFT) → 검수 → 승인(APPROVED) → 공개`

- AI는 근거에 연결된 과거 사실의 설명 초안을 만든다. 가격·수익률 계산은 서버가 한다. 근거 없이 가격 변동의 원인을 단정하지 않는다.
- 근거 ID, 모델·프롬프트 버전, 입력 데이터 버전 또는 해시, 생성 시각, 검수·승인 상태를 저장한다. 입력이 같은 재시도에서는 중복 생성을 막는다.
- 화면에는 승인된 해석만 공개한다. AI 생성 실패·검수 대기 중에도 시세 조회와 시뮬레이션은 동작한다. 핀 공개 기준을 충족한 사건은 기존 규칙에 따라 날짜·등락률만 표시할 수 있다.
- 근거가 정정되면 기존 설명을 재검토 대상으로 표시한다. 오류가 확인된 승인본은 노출을 중단하고, 새 승인본이 나오기 전까지 검증된 수치만 제공한다.

## 6. 스케줄러와 실패 복구

| 항목 | 규칙 |
|---|---|
| 일정 | 적금·시세·뉴스·AI 작업을 분리한다. 시간대는 Asia/Seoul을 명시한다. 정확한 실행 시각은 제공처 갱신 시각·호출 제한 확인 후 확정한다. 기존 03의 시각은 초안이다. |

| 재시도 | 일시 오류·호출 제한에 대기 후 제한된 횟수로 재시도한다. 제공처의 재시도 지시를 따르고 인증·계약 오류를 무한 재시도하지 않는다. |
| 재개 | 마지막 완료 페이지·날짜·종목을 기록한다. 페이지 구성이 변할 수 있으면 해당 범위를 다시 받아 중복 없이 저장한다. |
| 정정 수집 | 성공한 기준일도 명시적인 재수집·정정 실행을 허용한다. 성공 기록이 있다는 이유로 영구히 건너뛰지 않는다. |
| 공개 | 적금은 검증 완료 결과를 전환하고, 시세는 검증된 종목·거래일 범위를 제공한다. 미완료 범위를 최신 데이터로 표시하지 않는다. |
| 장애 | 마지막 성공 데이터를 유지한다. 시세·적금·뉴스·AI별 기준일과 갱신 상태를 구분하며 한 작업의 실패가 다른 조회를 막지 않게 한다. |
| 운영 기록 | 실행 ID, 작업·대상 범위, 시작·종료 시각, 조회·추가·변경·실패 건수, 재개 위치, 오류 요약을 남긴다. 키와 기사 원문을 오류 로그에 넣지 않는다. |
| 자원 | API 호출 동시성·DB 저장 건수·worker 메모리·DB 연결 풀 상한을 둔다. DB 확정 뒤 실제 데이터로 측정한다. |

## 7. 구현 전 결정할 것과 검증 기준

미정 항목:

- 웹 DB 엔진·호스팅·용량·백업·복원 방식과 데이터별 보존기간
- 자동 갱신의 이번 개발·해커톤 포함 여부, 담당자와 완료 일정
- 적금·시세·뉴스 제공처별 실제 응답, 호출 한도, 과거 제공 범위, 이용 조건
- 작업별 실행 시각, 페이지·저장 크기, 재조회 기간과 재시도 상한
- 뉴스 중요도·종목 연결·차트 거래일 연결 기준, 검수 담당과 처리 주기

구현 후에는 다음을 확인한다. 이 목록은 아직 통과한 검사 결과가 아니다.

- 같은 데이터를 반복 수집하거나 작업이 겹쳐도 상품·옵션·시세·기사·해석이 중복되지 않는다.
- 중간 페이지 실패 후 재개해도 누락이 없고, 기존 상품이 잘못 종료되거나 불완전한 적금 목록이 공개되지 않는다.
- 휴장일·제공처 갱신 지연·과거 정정·뉴스 정정·장 마감 후 기사·다른 회사의 동명 기사를 처리한다.
- AI 실패·검수 대기 때도 조회·계산이 가능하며, 승인 전 해석이나 오류가 확인된 설명이 공개되지 않는다.
- 화면의 기준일·갱신 시각·지연 표시는 실제 수집 상태와 일치한다. 운영 데이터로 확인하기 전에는 자동 갱신이 운영 중이라고 보고하지 않는다.
